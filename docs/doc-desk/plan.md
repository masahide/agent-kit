# doc-desk Mod 計画書

作成日: 2026-09-22 / 更新: 2026-09-24 (名前を document-interview から doc-desk に変更。2026-09-23: 実装しなかった設計と将来の計画を削除。文書の検査表、Windows 対応、指摘モードの設計と実装を追加) / 状態: 背景と決定の記録。実装の説明は [plugins/doc-desk/README.md](../../plugins/doc-desk/README.md)、使い方は [usage.md](usage.md) にあります

## 要点

- 文書を書く前に Claude が論点を整理し、一枚のフォームとして人に出し、人がまとめて答え、その回答を Claude が読んで設計書・仕様書・企画書・記事を書く仕組みを、Claude Mods として作りました。
- 元ネタは 3 つです。akapen からは「決定だけを人に聞く」出題規律と回答の固定形と試問を、grilling-viz からは質問データの型と回答の保持を、ja-text-communication からは質問文と生成文書の日本語規範を引き継ぎます。
- 生成文書の検査には、AI 臭 (生成 AI が書いた文章に出やすい癖) を消すスキル stop-ai-slop-jp と humanizer-ja の規則も取り込みます。元のスキルは同梱せず、決定を記録する文書に合う規則だけを書き直しました (2.4 節)。
- 当初はペインの中で答える設計でしたが、検証 (4 章) を経て、ブラウザの HTML フォームで答えて受信サーバに POST で戻す経路にしました。回答はツールの結果か、`$.prompt.submit` による user turn で Claude に届きます。
- 書き上げた文書に、人が画面で指摘を付けて返す指摘モードを足します。設計を 2026-09-23 に決め (3 章の「指摘モードの設計」)、同じ日にツール `open_review` として実装しました。

| 完了報告 | Claude が文書を書き終えたときに、書いた文書と決めたことをまとめて人に示す報告です。SKILL.md の手順の最後にあたります。 |
| 指摘モード | 書き上げた文書を人に見せ、段落や文字列に直してほしいことを付けて返してもらう段階です。 |
| 指摘の画面 | 指摘モードで人が見る Review Workspace の画面です。左に文書、右に指摘の操作が出ます。 |
| 宣言 | 人が、そのセッションでこの Mod を使うと示すことです。宣言した後は、文書を書き終えるたびに、完了報告の前に指摘の画面が自動で出ます。 |
| 段落番号 | Mod が文書の HTML の段落に上から振る番号です。人の指摘は、この番号で Claude に届きます。 |
| チップ | 指摘の種類を表す、短い言葉のボタンです。押すと、その種類の指摘になります。 |
| 添削 | 人が本文をその場で書き換えて返すことです。akapen の添削モードにあたります。 |

## 1. 背景と目的

### 1.1 いまの往復と、その限界

akapen と grilling-viz はどちらも「質問を HTML 1 枚にしてブラウザで開き、人が答え、生成されたテキストをターミナルに貼る」往復です。この往復は次の点で重いです。

- 人がブラウザとターミナルを行き来します。回答のテキストをコピーして貼る操作が毎回入ります。
- 回答の下書きは `localStorage` に残りますが、Claude 側からは見えません。

ja-text-communication は日本語で書くときの規範集で、UI や往復の仕組みは持ちません。質問文と生成文書の品質を上げる材料として使います。

### 1.2 Mods で変わること

Claude Mods では、plugin がツールを登録し、外部プロセス (受信サーバ) を起動し、`$.prompt.submit` で Claude に user turn を投入できます。これにより、ブラウザで [送信] を押すだけで回答が Claude に届き、コピーと貼り付けが要らなくなります。

### 1.3 目的

1. 文書作成前の論点整理を、人の判断コストを最小にした一枚のフォームで行えるようにします。
2. 人の回答を、コピーと貼り付けなしで Claude に渡せるようにします。
3. 回答をもとに Claude が文書を生成・更新する手順を、スキル (SKILL.md) として固定します。

### 2.1 akapen から引き継ぐもの

| 証跡として HTML を残す | `./doc-desk/<label>.*` に質問票、HTML、回答を保存する |

| 規範 | Mod での適用点 |

| B2, B4: 英単語に助詞を直結しない、造語を作らない | 質問文の自己検査表 (`references/question-lint.md`) |

| D4: 数値には単位・分母・範囲を添える | 判断材料の数値の書き方。`cite` 欄に範囲を書く |
| E2, E7: 要点先行、確認質問には判断材料を添える | 結論ボックスと、選択肢ごとの `pros` と `cons` |
| F2, F3: 推測と事実を分け、一次情報を優先する | `cite` 欄の必須化と、試問の「引用の有無」検査 |
| H1: ユーザーの指定語を一字一句そのまま使う | 回答固定形に人の自由記述を改変せず載せる |
| 全体: 生成文書の文章規範 | 文書の検査表 (`references/document-lint.md`) の 1 章と 2 章。ja-text-communication のスキル本体は同梱しないので、規範ごとの要約を表に書く |
| G2: 変更の報告を差分と一対一に対応させる | SKILL.md の完了報告。既存の文書を更新したときは、変えた節と理由の一覧を出す |

### 2.4 stop-ai-slop-jp と humanizer-ja から引き継ぐもの

stop-ai-slop-jp と humanizer-ja は、生成 AI が書いた日本語から AI 臭を消すための Claude のスキルです。AI 臭とは、定型の前置き、人ではなくモノを主語にした書き方、根拠のない強調など、生成 AI の文章に出やすい癖を指します。どちらのスキルも、ブログやエッセイを人の声で書き直すことを主な対象にしています。この Mod が書くのは決定を記録する文書なので、元のスキルは同梱しません。合う規則だけを `references/document-lint.md` の 3 章 (S1〜S24) に書き直しました。

| 引き継ぐもの | 元 | Mod での置き場所 |
|---|---|---|
| 修正の優先順位 (立場、主体、構造、語彙、記号の順に直す) | stop-ai-slop-jp | document-lint.md の 3 章の並び (決定、主体、構造、語彙、記号) と 5 章の通し方 |
| 結論の回避、全方位肯定、ヘッジの重ね、弱い否定、節ごとの保留文 | stop-ai-slop-jp | S1〜S5 (決定) |
| モノに人の動作をさせる書き方、翻訳調の分析動詞、一般論 | stop-ai-slop-jp | S6〜S8 (主体) |
| 主張や問いかけの見出し、定型の書き出しと締め、予告、対比と否定の演出、事実の後の意義の付け足し、3 つに揃える癖、書式の過剰 | 両方 | S9〜S14 (構造) |
| 生成 AI が好む抽象語、比喩の定型、カタカナ語とビジネス語、冗長な文末、強調の副詞、接続詞の重ね、論文調の自称 | 両方 | S15〜S21 (語彙) |
| ダッシュ、かぎ括弧、中黒の並列、絵文字 | 両方 | S22〜S24 (記号)。検索用の正規表現を 5 章の手順 4 に置く |
| 5 つの軸での自己採点 | stop-ai-slop-jp | 5 章の手順 5。点数ではなく、通過か不通過かを答える 5 つの問いにした。書き手の自己採点は甘くなるから (試問を設けた理由と同じ) |
| 書き終えた後の読み直し (音読、「AI が書いたと思うか」の自問) | 両方 | 5 章の手順 6 |
| 語彙と記号の検査を質問文にも当てる | 両方 | `references/question-lint.md` の通し方の手順 2 |

採用しなかった規則は、伝聞の文末、文末とトーンのムラ、毒と感情の表明、一人称、主語の省略などです。どれも ja-text-communication の規範 (F1、F2、B5、C2 など) とぶつかるか、決定を記録する文書の読者の役に立ちません。一覧と理由は document-lint.md の 4 章にあります。

## 3. 決定事項

2026-09-22 に、akapen の流儀で挙げた 4 問すべてについて推奨案を採用しました。その後の変更を「現在」の列に書きます。

| 問い | 決定 | 理由 | 現在 |
|---|---|---|---|
| Q1. 置き場所 | A. `plugins/doc-desk/` (このリポジトリ内) | vendor の元ネタと並べて差分を追えます。使うときは `--plugin-dir` で指定します | そのまま |
| Q2. 選択肢の部品 | A. ペインの `Select` 1 つ (値 = 選択肢 ID) | 全サーフェスで同じ挙動で、行数が少なくて済みます | ブラウザ経路に変えたため不要。HTML の radio にした |
| Q3. 回答の見せ方 | A. 回答固定形の全文を user turn の本文にし、JSON を隠し context に添える | トランスクリプトに何を答えたかが残ります | 隠し context は成立しなかった (4 章 V7)。JSON は `doc-desk/<label>.answer.json` を読む |
| Q4. レビューモード (生成文書への段落ごとの指摘) の範囲 | A. 最初の範囲に含めない | MVP を小さく早く動かします。生成文書への指摘は当面チャットで受けます | 2026-09-23 に方針を変えた。指摘モードを足した (下の「指摘モードの設計」、ツール `open_review`)。続けて添削 (直接の書き換え) も足した (下の「添削の設計」) |

採用しなかった案は次のとおりです。Q1 は `~/.claude/skills/` への配置、Q2 は選択肢ごとの `Button`、Q3 は本文 1 行と隠し context だけ、Q4 は最初から含める案でした。

2026-09-22 には、答える面をペインからブラウザの HTML フォームに変えました。ペインの `Input` は 1 行だけで補足や表を書くには狭いこと、ブラウザ経路が検証 (4 章 V2, V4〜V6) で動いたこと、akapen のシートの形 (結論ファースト、問いカード) を HTML でそのまま使えることが理由です。ペインは、回答を待つ間の URL と状態の表示だけに使います。

2026-09-23 には、HTML フォームの画面を Review Workspace の形に作り直しました。akapen の紙面の形 (上から読み、下で答える) をやめ、左にレビューの対象、右に操作をまとめる形にしました。決めたことは次の 4 つです。

| 決めたこと | 決定 | 理由 |
|---|---|---|
| 書く前の段階で左に何を出すか | 構成案 (これから書く文書の見出しと各節の要旨) と、その中に番号付きの印で置いた未確定事項 (問い) | 人は、選んだ結果が文書のどこにどう出るかを見て判断できます。指摘モードを足すときも、左を書いた本文に替えるだけで済みます |
| 構成案の書き方 | Claude が HTML の断片で書く。使える要素と属性を絞り (`hooks/form/outline.ts`)、Mod の検証で違反を返す。画面ではブラウザが DOMParser で解析し、許可した要素と属性だけで組み直す | Markdown を描画する仕組みが要りません。印を `data-q` と `data-table` の属性で明示でき、指摘モードでは段落をそのまま単位にできます。Claude の HTML (調べた文書から紛れ込んだものを含む) は、トークン付きの画面で実行されません |
| 右 (Inspector) の中身 | 左で選んだものに応じて変える。印なら決定 (根拠、選択肢、AI の推奨と理由、補足)、表なら表の説明、何も選んでいなければ全体の進み具合と次に見る項目と全体へのコメント | 右を問いの一覧に固定すると、左の対象と右の操作がつながりません |
| 次に見る項目の順番 | 推奨案の無い未確認の問い、推奨案のある未確認の問い、空欄のある表の順。同じ順位の中では構成案の上から | 推奨案の無い問いは、人が答えないと AI が根拠なしに選ぶことになるからです |

色は意味ごとに分けました。青は選択と操作、赤は推奨からの変更と失敗、緑は確認済み、黄は未確認、灰は AI の推奨です。900px より狭い画面では、右を下から出る領域にします。

質問票には構成案 `outline` (必須) と、選択肢ごとに構成案の印に入る文 `preview` (任意) を足しました。まだリリースしていないので、`schemaVersion` は 1 のまま形を変えました。回答 JSON と回答固定形 v1 は変えていません。

2026-09-23 には、Mod を Windows でも動くようにしました。それまでの Mod は、4 つの操作をシェルのコマンドに頼っていました。

- 受信サーバの起動: `sh -c "nohup python3 …"`
- ブラウザを開く: `open` と `xdg-open`
- 前回の回答ファイルを消す: `rm`
- 受信サーバを止める: `kill`

これらのコマンドは、どれも Windows のプロセスからは見つかりません。また Windows の `python3` は、Python が入っていても Microsoft Store の案内だけを出すスタブに当たることがあります。そこで、OS ごとの違いを `receiver.py` のサブコマンド (`start`、`open`、`clean`、`stop`) に移し、Mod はシェルを使わずに `<python> receiver.py <サブコマンド>` だけを呼ぶようにしました。Python は `python3`、`python`、`py -3` の順に探します。

受信サーバを Node や Bun で書き直す案も比べましたが、採りませんでした。Mod の hooks は Node も Bun も使えない環境で動き (型定義 `claude-code.d.ts` の冒頭。Claude Code 2.1.277 の `/plugin-types` が書き出したもの)、Bun で作られた Claude Code の実行ファイルを Bun として動かす入口もありません。どちらの言語でも別に実行環境を入れる必要があります。Python のままなら、macOS と Linux の今の動きを変えずに済みます。

2026-09-24 に、Mod とスキルの名前を `document-interview` から `doc-desk` (文書の編集デスク) に変えました。指摘モードと添削を足したので、この Mod は書く前に論点を聞くだけでなく、書いた後に指摘を受けて直すところまで受け持ちます。前の名前は書く前の段階しか表さず、スキルの呼び出し (`/document-interview:document-interview`) も長いためです。新聞や雑誌の編集デスクは、書く前に方針を聞き、書いた後に赤を入れます。この役割が両方の段階に合います。コマンド (`/doc-desk`)、ペインの id、証跡のフォルダ (`doc-desk/`)、回答固定形の 1 行目 (`【doc-desk 回答】`) も同じ名前にそろえました。まだリリースしていないので、前の名前との互換は残していません。

### 指摘モードの設計

指摘モードは、書き上げた文書を Review Workspace の左に出し、人が段落や選んだ文字列に付けた指摘を受け取って、Claude が文書を直す段階です。2026-09-23 にツール `open_review` として実装しました (`plugins/doc-desk/hooks/review/`、手順は `skills/doc-desk/references/review-mode.md`)。設計は同じ日に、この Mod 自身を使い、2 枚の質問票で決めました。1 枚目で画面と流れを決め、2 枚目で、1 枚目の後に残った 3 点 (宣言とみなす発言、HTML ファイルの置き場所、長い文書の扱い) を決めました。質問票は `doc-desk/review-mode-design.json` と `doc-desk/review-mode-design-r2.json`、回答は `doc-desk/review-mode-design.md` と `doc-desk/review-mode-design-r2.md` です。このリポジトリでは `doc-desk/` を git の対象から外しているので、どれも作者の手元にだけあります。

決めたことは次の 10 項目です。

| 決めたこと | 決定 | 理由 |
|---|---|---|
| 指摘の画面を出すとき | 人がセッションの中でこの Mod を使うと宣言したら、それ以降は文書を書き終えるたびに、完了報告の前に自動で出す。宣言が無ければ、人が頼んだときだけ、完了報告の前に出す | 人の補足のとおりです (下の「人の補足」)。人は選択肢 B (頼んだときだけ出す) を選び、補足で宣言したときの扱いを足しました |
| 宣言とみなす発言 | 人がスラッシュコマンド `/doc-desk:doc-desk` でスキルを呼んだとき、または「この Mod でやろう」のように、この Mod を使うと文で頼んだとき。この Mod について尋ねただけの文は、宣言とみなさない。宣言かどうかは Claude が会話を読んで判定し、Mod は判定しない。宣言は、人が取り消すまでそのセッションの間続く | 2 枚目の回答で、人は選択肢 B (スラッシュコマンドに加え、使うと書いたときも) を選び、補足を付けました (下の「人の補足」)。人がふだんの言葉で書いても、宣言として受け取れます。Mod が判定しないのは、人がスラッシュコマンドでスキルを呼んだのか、Claude が自分でスキルを呼んだのかを、Mod のフックが区別できないからです。型定義 `claude-code.d.ts` の `skill.prompt` の説明では、`/name` と入力したとき、Skill ツールで呼んだとき、subagent に前もって読み込ませたときに、同じイベントが届きます |
| 左に出す文書の渡し方 | Claude が書き上げた文書を HTML に変換してファイルに書き出し、Mod がそのファイルを読んで表示する | 人は選択肢 B (HTML に変換して渡す) を選び、補足で HTML ファイルを介す形を提案しました。ファイルを介すと、全文をツールの入力に載せずに済み、書き出した HTML が証跡にも残ります。Mod に Markdown を表示する仕組みを足さずに済む点は、選択肢 B と同じです |
| HTML ファイルの置き場所と名前 | 証跡と同じ `doc-desk/` に `<画面の名前>.doc.html` として書き出し、消さずに残す。画面の名前は、質問票の名前 (`label`) と同じく Claude が画面ごとに付けるので、前のファイルを上書きしない | 2 枚目の回答で、人は選択肢 A (証跡と同じ doc-desk/ に置いて残す) を選びました。質問票や回答と同じ場所にまとまり、何に指摘したかを後で見返せます。代わりに、`doc-desk/` を git の対象から外していないリポジトリでは、指摘の画面を出すたびに未追跡のファイルが 1 つ増えます。名前の `.doc` は、Mod が書く画面の HTML と見分けるための印です |
| HTML の検査 | Mod が構成案と同じ許可リスト (`hooks/form/outline.ts`) で検査し、画面でもブラウザが同じく組み直す。文字数の上限は、構成案の上限 (20000 文字) とは別に、10 万文字 (タグを含む HTML の文字数) にする (下の「長い文書」) | 2026-09-23 に数えると、この節を足す前の plan.md が 11,834 文字、usage.md が 6,829 文字でした。HTML に変換するとタグの分だけ長くなるので、構成案の上限のままでは余裕がありません。10 万文字の数え方は質問票で聞いていません。構成案の上限と同じく、タグを含めた文字数で数えることにしました |
| 長い文書 | 1 回の指摘の画面に出すのは 10 万文字までにする。それより長い文書は、Claude が節の切れ目で区切り、何回かの画面に分けて出す | 2 枚目の回答で、人は選択肢 A (10 万文字までずつ、節の切れ目で分けて出す) を選びました。1 回の画面で読む量が 10 万文字までに収まります。代わりに、10 万文字を超える文書では、指摘の画面と送信が何回かに分かれます。表示にかかる時間は、2026-09-23 に作者の PC (Windows 11) のブラウザで測ると、10 万文字で 0.1 秒、140 万文字で 1.6 秒でした。測ったのは、画面が HTML を許可リストで確かめながら表示し終えるまでの時間です |
| 指摘の付け方 | 段落を押すか文字列を選ぶと、右に指摘の操作が出る。人はチップを選び、必要ならコメントを 1 行書く。指摘を付けた段落には指摘の通し番号の小さな印を付け、本文を赤字で埋めない | 本文を読みやすいまま残し、指摘の中身は右に集めます (画面の作り直しで共有された提案) |
| 使うチップ | 短くする、言い換える、分かりやすく、具体例を足す、根拠が要る、削る、順序を入れ替える、図を直す、ここは良い の 9 種 | 人が表で 9 種すべてを「使う」にしました |
| 直接の書き換え (添削) | 指摘モードが動いてから、次の実装で足す (2026-09-23 に足した。下の「添削の設計」) | 作る量の目安として、akapen の添削の画面 (`assets/tensaku/template.html`、101,480 バイト) は、指摘の画面 (`assets/shiteki/kit-template.html`、28,662 バイト) の約 3.5 倍あります |
| 書く途中で見つけた論点 | 今までどおり 2 枚目の質問票で先に聞き、答えを反映してから文書を仕上げる。指摘の画面には問いを置かない | 指摘の画面を指摘だけに絞ると、仕組みが単純になります |

回答固定形の末尾には、指摘の節 (`## 指摘`) を足します。1 行は `#段落番号 [チップ] 「選んだ文字列」 コメント` の形で、akapen の【赤ペン回答】をもとにします。段落番号は、Mod が HTML の段落に上から振った番号です。文書を分けて出したときは、Mod は画面ごとに 1 から番号を振ります。次の例は、この節のために作った架空のものです。

```
## 指摘
#3 [短くする]
#7 [根拠が要る] 「応答が速くなる」 何秒から何秒になるかを足してほしい
#12 [ここは良い]
```

指摘の場所は、Claude が段落の文字列を元の Markdown と照らし合わせて探します。Claude は指摘に沿って文書を直し、「ここは良い」の指摘が付いた箇所は直しません。完了報告には指摘を 1 件ずつ並べ、それぞれに直した箇所か、直さなかった理由を添えます。

人の補足 (回答のまま):

- 指摘の画面を出すとき: 「このプラグインを使うことをそのセッションで宣言した時は以降は自動で完了報告の前に出す。そうではない場合はユーザーが頼んだ時に完了報告の前に出す」
- 左に出す文書の渡し方: 「claudeがHTMLファイルに出力してそのファイルをmodが利用する形はどう？」
- 宣言とみなす発言 (2 枚目): 「スラッシュコマンドを読んだセッションでは基本的には資料完成前に実行する」

この文書では、2 枚目の補足を次の意味に取りました。スラッシュコマンドでスキルを呼んだセッションは宣言のあるセッションなので、基本的には資料完成前 (文書を書き終えた後、完了報告の前) に指摘の画面を出します。表の「指摘の画面を出すとき」の決定と同じ扱いです。

採用しなかった案は次の 7 つです。後の 3 つは 2 枚目の質問票の選択肢です。

- 文書を書き終えるたびに必ず出す案。人はこれを選ばず、補足で、宣言したときだけ毎回出す形にしました。
- Markdown のファイルを Mod が読んで表示する案。Mod に Markdown を表示する仕組みを足す必要がありました。
- 直接の書き換えを指摘モードと同時に入れる案。書き換えの入力欄、書き換えた文を返す回答の節、元のファイルへの反映を同時に作ることになります。
- 指摘の画面にも問いの印を置く案。文書の中に問いを置く書き方と、指摘と答えが並ぶ回答の形を新しく決める必要がありました。
- スラッシュコマンドでスキルを呼んだときだけを宣言とみなす案。判定に迷いはありませんが、「この Mod を使う」と書いても宣言になりません。
- HTML ファイルを OS の一時フォルダに置き、反映したら消す案。何に指摘したかの記録が残らず、回答の段落番号だけが残ります。
- 長い文書も分けずに 1 回で出す案。上限は、Mod がファイルを読める 4 MiB になります (型定義 `claude-code.d.ts` の `$.fs.read`)。日本語の文字は UTF-8 で 1 文字 3 バイトなので、およそ 140 万文字です。長い文書では、1 回の画面を読んで指摘し終えるまでの時間が長くなります。

実装では、設計に無かった次の 3 点を足しました。

- 回答の `## 指摘` の後に `## 指摘した段落` の節を置き、指摘の付いた段落の文字列 (400 文字まで) を載せます。段落番号はブラウザが振るので、Claude が番号から段落を探せるようにするためです。
- 回答の 2 行目に `対象: doc-desk/<label>.doc.html` を置き、分けて出した画面では `(2/3)` のように何回目かを添えます。user turn で届いたときに、どの画面の指摘かを見分けるためです。
- チップは必須にしていません。チップかコメントのどちらかがあれば指摘を足せます。9 種のどれにも当たらない指摘を、コメントだけで書けるようにするためです。

### 添削の設計

添削は、指摘の画面で人が段落をその場で書き換え、消し、足し、動かして返せるようにする機能です。指摘モードの次の実装として、2026-09-23 にこの Mod の質問票で決め、同じ日に実装しました (回答の形は `skills/doc-desk/references/review-mode.md` の 5 章)。質問票は `doc-desk/tensaku-design.json`、回答は `doc-desk/tensaku-design.md` です。

決めたことは次の 6 項目です。

| 決めたこと | 決定 | 理由 |
|---|---|---|
| 書き換える対象 | 段落の文字を、書式なしの文として書き換える。太字やコードの印は、Claude が元の文書を見て付け直す | 人は選択肢 A を選びました。指摘の画面が受け取るのは Claude が書き出した HTML だけで、元の文書の Markdown は受け取りません (`hooks/review/document.ts`)。今の画面と HTML の規則のまま作れます |
| 回答での表し方 | 回答に「書き換え」の節を足し、段落ごとに書き換える前と後の全文を「前:」と「後:」の行で載せる | 人は選択肢 A を選びました。Claude は前の文を、指摘と同じく書式の印を無視して元の文書と照らし合わせ、後の文に置き換えます |
| 段落の足し引き | 書き換えのほかに、段落の削除、段落の下への追加、段落の移動 (指定した段落の後へ) ができる | 人は選択肢 B (削除と追加) を選び、補足で移動を足しました (下の「人の補足」) |
| Claude の反映 | 書き換えた後の文と足した文は、文字を一字一句そのまま元の文書に入れ、言い換えない (「参考にして直す」を選んだものを除く。下の「書き換えた文の使い方」)。削除と移動は指定どおりに行う | 人が書いた文だからです (ja-text-communication H1) |
| 指摘との関係 | 同じ段落に、書き換え (か削除) と指摘の両方を付けられる。書き換えと削除は同じ段落に 1 つだけ | 書き換えた段落を消すことは無いので、2 つは排他にします |
| 書き換えた文の使い方 | 書き換えと追加ごとに、人が「そのまま使う」(既定) か「参考にして直す」を選ぶ。そのままなら一字一句そのまま入れ、参考にして直すなら、Claude が意図に沿って前後の文に合う文を書き、完了報告で人の文と並べて示す | 質問票の後に、人から 2 種類ほしいと頼まれました (2026-09-24)。既定をそのままにしたのは、人が書いた文を言い換えないという上の決定と合わせるためです |

人の補足 (回答のまま):

- 段落の足し引き: 「この部分を削除したいとか、この部分をｘｘｘに移動したいとかを指定されたらその通りに修正してもらえるようにしたい」

採用しなかった案は次の 3 つです。

- 段落ごとの Markdown を画面に渡し、Markdown を書き換える案。Claude が HTML に加えて段落ごとの Markdown を書き出す必要があり、HTML の規則と画面の作りが増えます。
- 回答に変わった語だけを載せる案。Mod に語の差分を取る処理が要り、同じ語が段落に 2 回あると、どちらを変えたかが分かりにくくなります。
- 書き換えだけにする案。段落を消したり動かしたりしたいときに、指摘のコメントで伝えることになります。

## 5. ライフサイクル拡張の記録

[lifecycle-plan.md](lifecycle-plan.md) の段階を終えるごとに、決めたことと実機で確かめたことを 1 節ずつ足します。

### 段階 0: 受信サーバの起動を単純にする (2026-09-24)

- `receiver.py start` は `serve` の stdout だけを pipe で受け、`serve` が listen 直後に出す `{"port": n, "pid": n}` の 1 行を写して終わります。3 秒で 1 行来なければ `serve` を止め、何も出さずに終了コード 1 で終わります。Mod はこれを `failed` (受信サーバが port を返しませんでした) にします。port-file と、それを待つ `$.clock.after` の polling は消しました。
- `serve` は 1 行書いたら `sys.stdout.close()` に加えて `os.close(1)` をします。Python の標準出力は `closefd=False` で開かれているので、前者だけでは pipe が閉じず、`start` の読み取りが終わりません。
- Windows で `DETACHED_PROCESS` の子に `stdout=PIPE` を渡して 1 行読めることを確かめました (Python 3.14.2、`start` は 0.23 秒で戻った)。
- `serve --port <n>` を足しました (段階 1 で使う)。Windows の `SO_REUSEADDR` は使用中の port も取れてしまい、実際に同じ port で 2 つ目の受信サーバが起動しました。そこで Windows では `SO_REUSEADDR` を付けず `SO_EXCLUSIVEADDRUSE` を付けます。付けたあとは、使用中の port を指定すると別の port になり、TIME_WAIT だけが残る port は取り直せました。

### 段階 1: 未回答の引き継ぎ (2026-09-24)

- 待機を始めた時点で `$.store` の `pending:<cwd>` に記録を書き、回答が届くか取り消すと消します。計画どおり `session.end` は使いません。
- 起動時に回答が届いていて人がいるときは、記録を `/doc-desk` で送るまで残します。人が `/doc-desk` を打たずにまた閉じても、次の起動で同じ案内が出ます。
- `command.run` の中で `$.prompt.submit` を呼ぶと、エンジンが「このフックが握っている turn を待つことになる」として拒みました (テストキットの host check)。`/doc-desk` は `$.clock.after(0)` でコマンドが終わった後に送ります。これで段階 0 で消した `$.clock.after` が、別の役目で戻りました。`session.start` の中の `$.prompt.submit` は拒まれないので、`-p` と SDK では待たずに (`void`) 呼びます。
- 受信サーバの生死は `GET /wait?timeout=0` で見ます。`$.http.fetch` に時間の上限を渡す欄は無いので、死んでいるときは接続拒否ですぐ失敗することを当てにしています。
- 実機で確かめていないこと: `session.start` の中の `$.ui.toast`、`$.ui.log` の見え方と、起動直後の `$.prompt.suggest` が薄い候補として出るか。テストキットでは通っています。
- レビューを受けて直したこと (2026-09-24):
  - 同じフォルダで 2 つのセッションが同時に動くと、両方が同じ待機を引き継ぎ、片方の取り消しが相手の受信サーバを止めた。レビューの案「セッション id が違えば引き継がない」は、別のセッションで引き継ぐという段階 1 の目的と両立しないので、記録に持ち主の id と heartbeat の時刻を持たせ、別のセッションが今も持っている (heartbeat が 90 秒以内) ときだけ引き継がない形にした。キーも `pending:<cwd>:<セッション id>` に分け、互いの記録を上書きしないようにした。
  - 生死の確認が失敗したとき、古い pid に `stop` を打つ案は採らなかった。pid が他のプロセスに使い回されていると、無関係なプロセスを止めてしまう。代わりに同じ port で起動し直し、port を取れなかったら古い方が生きていると判断して、起動し直した方 (pid が確か) を止める。
  - `-p` と SDK、`/doc-desk` は、投入が受け付けられてから記録を消し、失敗したら未送に戻す。
  - 同期待ちで回答を読んでいる間に差し替えや取り消しがあれば、その回答は届けない (差し替え先の記録やペインを触らない)。
  - キーの cwd を正規化し、案内の文言を画面の種類 (質問票か指摘の画面か) に合わせた。

### 段階 2: 回答行を畳む、回答先を添える、届いたら知らせる (2026-09-24)

- `turn.complete` の `{ text }` は、型定義 (2.1.280) の説明「Return `{ text }` with a different text to show it beneath the answer」で「答えの下に出る」と読めたので、答えを置き換えない前提で作りました。
- matcher の入れ子 `{ component: 'UserMessage', props: { origin: { kind: 'plugin' } } }` は validate が `props.origin has {kind=plugin}` と読みました。フックの中でも `origin.name` が `doc-desk` かを見て、他の plugin の投入は素通しします。
- 畳んだ行に出す `.md` のパスは、このセッションで届けた固定形だけ覚えています。固定形の見出しは documentId で、label (ファイル名) とは限らないからです。resume した会話の古い行は、パス無しで畳みます。
- 回答が届いたときの通知は、同期経路と非同期経路の両方で出します (`settle` で出すため)。
- 実機で確かめていないこと: plugin の投入した行で `UserMessage` の描き換えが呼ばれるか。テストキットでは terminal と desktop の両方で通っています。

### 段階 3: 圧縮で決定を残す (2026-09-24)

- 計画は上限を超えたとき「各 `.md` の `## 決定` の節だけにする」でしたが、回答固定形に `## 決定` の節はありません。代わりに「決定の部分」を固定形の規則から取り出します。質問票は見出しと `Qn.` の行 (表と全体へのコメントを外す)、指摘の画面は見出しと対象、`## 指摘` の節、`## 書き換え` の各項目の見出し行 (`前:` と `後:` の全文を外す) です。決定の部分の後には全文の `.md` のパスを添えます。
- 「このセッションで届いた回答」は、Claude に届けた時点で数えます。起動時に見つけて `/doc-desk` を待っている回答は、送るまで入れません。同じ label が 2 回届いたら新しい方だけを残します。
- 計画どおり、届いた回答が無ければ `next(e)` を返し、回答待ちの画面だけがあるときも何も足しません。
- テストキットの `$.session.compact` は `trigger` と `messages` を含む入力をそのまま取るので、`agentId` 付きの圧縮もテストできました。
- 実機で確かめていないこと: 組み立てた message を足した後の turn が、それを読むか (`/compact` の後に尋ねる)。
- レビューを受けて直したこと (2026-09-24): 回答待ちの注記に回答先の URL と画面の種類を入れた (圧縮で Tool result と `turn.complete` の URL が消えるため)。結果に前の記録が残っていれば除いてから足し、記録が 2 重にならないようにした (`precompute` の後に本番の圧縮が来たときなど)。切り詰めでも人が埋めた `## 表` は決定として残す。`{ skip }`、同じ label の 2 回目、`.md` が消えた場合のテストを足した。

### 段階 5: 自己指摘の候補を先に出す (2026-09-24)

- 型定義 (2.1.280) の `ModelForkRequest` は `prompt` だけで、`timeoutMs` はありません。fork は時間の上限なしで待ちます。`$` 呼び出しの待ちなのでフック予算には数えない前提です (実機では未確認)。

- テストキットには plugin の `options` を渡す口が無いので、「設定かツールの入力のどちらかが false なら作らない」を純粋な関数 `wantsSelfReview` にし、単体で確かめました。
- `numberedBlocks(html)` は、許可リストの要素に効く暗黙の閉じ (`<p>`、`<li>`、`<dt>`/`<dd>`、`<tr>`、`<td>`/`<th>`)、`<pre>` 直後の改行、文字参照を真似る小さな木の組み立てで作りました。実ブラウザ (Claude デスクトップアプリ内蔵の Chromium) で、入れ子の箇条、暗黙の閉じ、`pre`、空の表の行を含む HTML の段落番号 1〜15 と文字列が一致することを確かめました。候補の [採用]、[却下]、全体へのコメントの候補、下書きの復元も同じ画面で確かめました。

- レビューを受けて直したこと (2026-09-24): fork を待つ間の中断を見て、受信サーバやブラウザを出さずに `cancelled` を返す。テストキットからはツールの呼び出しを中断できないので、中断の印として fork の `aborted` も見る (実機ではその turn の中断で返る)。返答の JSON はコードフェンスを先に探し、無ければ `[` ごとに試す (前置きの `[S3, S15]` で候補が全滅しないように)。範囲外の数値文字参照で `numberedBlocks` が例外を投げないようにし、よく使う名前付き文字参照を足した。`.candidates.json` を結果の `files` に載せ、候補を作らないときは前回のものを消す。`(Claude の候補)` の印は `format.ts` の定数を画面の JS に埋めて 1 か所にした。
