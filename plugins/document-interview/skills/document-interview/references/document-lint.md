# 文書の検査表 (ja-text-communication の規範と AI 臭の検査)

手順 6 で文書を書くときに使います。書く前に 1 章の 4 つを決め、書いた後に 5 章の順で検査して直します。

この表の番号は 2 種類です。A〜H は ja-text-communication (mathbullet が公開している、日本語で書くときの規範集) の規範番号です。規範の本体はこの plugin に入っていないので、各行に要約を書いています。S1〜S24 は AI 臭の検査です。AI 臭とは、生成 AI が書いた文章に出やすい癖のことで、定型の前置き、人ではなくモノを主語にした書き方、根拠のない強調などを指します。S の項目は、AI 臭を消すための Claude のスキル stop-ai-slop-jp と humanizer-ja から、決定を記録する文書に合うものを選んで書き直したものです。選ばなかった規則と理由は 4 章にあります。

質問票の自己検査 (`references/question-lint.md`) は質問票の欄を対象にします。この表は、回答を反映して書く文書の本文を対象にします。ja-text-communication の G (作業報告) は SKILL.md の「完了報告」で扱います。E5、E7、H5 は会話での受け答えについての規範なので、この表では扱いません。

## 1. 書く前に決めること

| 決めること | 決め方 | 対応する番号 |
|---|---|---|
| 読者 | 試問で使った読者宣言 (`references/preflight.md`) をそのまま使います。その読者が知らない語は、文書の用語の節で定義します | H3 |
| 冒頭の一文 | 文書全体の結論を 1 文で書きます。質問票の `conclusion` を、回答で確定した内容に書き直したものです | E2 |
| 各節で言い切る決定 | 節ごとに、読者が「いや、別の案にすべきだ」と反論できる具体的な決定を 1 つ持ちます。決定を持てない節は、事実の記録か用語の定義だけの節にするか、消します | E1、S1 |
| 質問票から引き継ぐもの | `glossary` は文書の用語の節に、`cite` は本文の典拠に、各問の回答は「決定事項」の節に移します。選択肢の `label` の語と、人が補足に書いた語は、文書でも同じ語で書きます | A5、D5、F1、H1 |

## 2. ja-text-communication の規範による検査

| 番号 | 規範 | 文書での検査 | 落ちる例 → 直し方 |
|---|---|---|---|
| A1 | 専門用語・略語は初出で定義する | 略語と専門用語が、初めて出る箇所か用語の節で 1 行で定義されているか | `OIDC に統一します` だけ → 用語の節に OIDC の定義を 1 行で書く |
| A2 | 固有名詞は初出で位置づけを添える | 製品名・ライブラリ名・他の文書名の初出に、それが何で、なぜここに出るかが書いてあるか | `Keycloak を使います` → `認証サーバには Keycloak (オープンソースの認証サーバ製品) を使います` |
| A3 | 書き手が導入した内部要素は読者にとって未知 | 質問票の ID (`q1`, `tb1`)、変数名、関数名を説明なしで本文に出していないか | `q1 は A で確定` → `既存ユーザーは初回ログイン時に自動で移行します (質問票 spec-auth-01 の問 1、推奨案で確定)` |
| A4 | 業界の常識を前提にしない | 「一般的な構成」「通常の手順」で説明を済ませている箇所がないか | `通常どおりリフレッシュトークンを使います` → リフレッシュトークンを定義し、この文書で何日有効にするかを書く |
| A5 | 成果物ごとに用語を再導入する | 質問票の `glossary` で定義した語を、文書でも定義し直しているか | 質問票で定義済みだからと文書の用語の節を省く → 同じ定義を文書にも書く |
| B1 | 英語術語は定訳、定着したカタカナ、英語のまま、の順で選ぶ | 書き手が独自に作った訳語がないか | 定訳が見つからない術語を `前進認証` と訳す → 英語のまま `pre-authentication` と書き、用語の節で説明する |
| B2 | 英単語に助詞・活用を直結しない | `migrate する`、`generic な` のような書き方がないか | `session を migrate する` → `セッションを移行する` |
| B3 | 訳語だけで意味が通るか | 訳した語だけを読んで意味が取れるか | `ハイブリッド方式` → `自動移行と再登録を併用する方式` |
| B4 | 造語・圧縮熟語・俗語・比喩を使わない | 「〜に寄せる」「〜に落とす」「〜を流す」のような語がないか (比喩の定型は S16 も見る) | `OIDC に寄せる` → `OIDC に統一する`。`ログを流す` → `ログを送る` |
| B5 | 敬体で一貫させる | 文末が「です・ます」で揃っているか。体言止めのメモ調が混ざっていないか | `移行失敗時は再試行` → `移行に失敗したときは再試行します` |
| C1 | 一文一義 | 1 文に複数の事実や決定を詰めていないか | `OIDC に統一し、移行は 2 週間で、ログは 90 日保持します` → 3 文に分ける |
| C2 | 主語・目的語・授受を省かない。体言止めの圧縮句で判断を表さない | 各決定に、誰 (どの役割、どのコンポーネント) が何をするかが書いてあるか | `期限切れ時は再発行` → `セッションの期限が切れたら、認証サーバがトークンを再発行します` |
| C3 | 矢印連鎖の前提を先に書く | `A → B → C` の各矢印の前提が本文に書いてあるか | `ログイン → 移行 → 旧セッション削除` → 各段階で何が起き、次に進む条件が何かを文で書く |
| C4 | 表のセル・括弧・見出しに未説明の圧縮表現を置かない | 表の列名から、何の値かが分かるか。セルに略語や記号だけを置いていないか | 列名 `要否` → `認証 (必要 / 不要)` |
| D1 | 指示語より固有名 | 「これ」「上記」「その方式」が何を指すか一意に分かるか | `上記の方式で移行します` → `初回ログイン時の自動移行で移行します` |
| D2 | 重要な区別を助詞や含みで表さない | 残すか消すか、移すか複製するかの区別が、独立した文で書いてあるか | `旧セッションも扱います` → `旧セッションは移行期間 (2 週間) のあいだ残し、その後消します` |
| D3 | パスは読み手の座標系で書く | パスがリポジトリ直下からの相対パスか、絶対パスか | `session.ts` → `src/auth/session.ts` |
| D4 | 数値に単位・分母・範囲を添える | 数値に単位と、何に対する値かが付いているか | `4 倍になります` → `保存費用が、保持期間 90 日のときの約 4 倍になります` |
| D5 | 同一概念に同一の語 | 同じものを「利用者」「ユーザー」「会員」と呼び分けていないか。質問票と文書で語が揃っているか | 質問票で「既存ユーザー」、文書で「旧会員」 → 質問票の語に揃える |
| E1 | 主張には理由を添える | 各決定に理由があるか。理由が書けない決定を、推測として扱っているか | `認証は OIDC に統一します` だけ → `自前のセッション管理が、9 月の障害 2 件の原因だったからです (docs/ops/incidents.md:3-20)` を続ける |
| E2 | 要点先行 | 文書の冒頭に結論の一文があるか。各節の最初の文が、その節の結論か | 背景から書き始める → 冒頭に `認証は OIDC に統一し、既存ユーザーは初回ログイン時に自動で移行します` を置く |
| E3 | 主張を先に、根拠を後に書く | 根拠 (引用、データ) を先に並べ、結論を後に置いていないか | 障害記録の引用から始まる節 → 決定を先に書き、引用を後に置く |
| E4 | 見出しと内容を一致させる | 見出しの下に、その見出しの内容だけがあるか | 「移行手順」の節にログの保持期間の決定がある → 「運用」の節に移す |
| E6 | 前後の記述と矛盾させない | 冒頭の結論、決定事項、本文が食い違っていないか。2 枚目の回答で変わった決定が、全部の箇所に反映されているか | 冒頭で「移行期間は 2 週間」、本文で「1 か月」 → 回答を確かめて一方に揃える |
| F1 | 事実には典拠を付ける | 事実の文に `file:line`、実行結果、回答のどれかが付いているか。「〜と言われています」がないか | `移行は難しいとされています` → 典拠のある事実に書き換えるか、消す |
| F2 | 推測と事実を分ける | 確かめていないことを、事実の言い方で書いていないか | `利用者は約 1 万人です` (未確認) → 確かめて `利用者は 12,340 人です (users テーブルの件数、2026-09-22 時点)` と書く。確かめられないなら `利用者数は未確認です (推測では約 1 万人)` と書く |
| F3 | 一次情報を優先する | 典拠が原典 (コード、設定、実測) か | README の記述を引く → 設定ファイルの該当行を引く |
| F4 | 典拠の内容と書き手の解釈を分ける | 引用の直後に、書き手の解釈が区別なく続いていないか。自作の例を事実のように書いていないか | 引用と解釈を別の文にし、解釈は `この文書では〜と判断します` の形で書く |
| F5 | 日付とバージョンを現時点で確かめる | 実測値に取得日が、バージョンに依存する記述に対象のバージョンが付いているか | `最新版で確認` → `Claude Code 2.1.278 で確認 (2026-09-22)` |
| H1 | 人が指定した語を一字一句そのまま使う | 依頼文、補足、全体へのコメントに出た語を言い換えていないか | 人が「ログイン画面」と書いたのに本文で「認証画面」と書く → 「ログイン画面」に揃える |
| H2 | セッション内の合意と矛盾させない | 会話や回答で決まったことを、文書で未決や別案として書いていないか | 回答で決めた保持期間を「今後検討」と書く → 決定として書く |
| H4 | 典型パターンより目の前の文脈 | この文書に要らない定型の節 (「今後の展望」「テスト方針」など) を置いていないか | 中身の無い「今後の展望」の節 → 消す |

## 3. AI 臭の検査

5 つの群に分け、直す順に並べています。語彙や記号だけを直しても、決定と主体が欠けている文書は、読者の判断材料になりません。

### 3.1 決定

| 番号 | 検査 | 見る箇所 | 落ちる例 → 直し方 |
|---|---|---|---|
| S1 | 結論を避けない | 「ケースバイケース」「場合によります」「一概には言えません」で決定を避けていないか | `キャッシュの有効期間は場合によります` → `キャッシュの有効期間は 5 分です。管理画面だけはキャッシュしません` |
| S2 | 全方位肯定をしない | 「どちらにも良さがあります」「メリットもデメリットもあります」で終わる段落がないか | 採用した案と理由を書く。採用しなかった案は「採用しなかった案」の節に理由付きで書く |
| S3 | 曖昧な断言と、根拠のない強い評価を書かない | 「本質的な課題」「重要な役割を果たします」「非常に有効です」「画期的」がないか | `OIDC は認証の本質的な課題を解決します` → `OIDC にすると、パスワードの保存と再発行の処理 (src/auth/password.ts) が要らなくなります`。何が、どれだけ、なぜ、が書けない文は消す |
| S4 | ヘッジを重ねない。弱い否定で逃げない | 1 つの段落に「〜可能性があります」「〜場合があります」「〜とは限りません」が 2 つ以上ないか。禁止事項を「注意が必要です」「推奨されません」で書いていないか | `トークンを localStorage に置くことは推奨されません` → `トークンを localStorage に置きません。画面に埋め込まれたスクリプトから読めるからです`。不確かなことは F2 のとおり未確認と書く |
| S5 | 保留の決まり文句を節ごとに置かない | 各節の末尾に「環境によって結果は異なる可能性があります」のような文がないか | 決まり文句を消す。本当に確かめていないことは「未確認事項」の節にまとめる |

### 3.2 主体

| 番号 | 検査 | 見る箇所 | 落ちる例 → 直し方 |
|---|---|---|---|
| S6 | モノに人の動作をさせない | 無生物が「示す」「もたらす」「浮き彫りにする」「導く」の主語になっていないか | `障害記録が自前セッションの限界を浮き彫りにしました` → `障害記録 (docs/ops/incidents.md:3-20) によると、9 月の障害 2 件はどちらもセッションの期限切れ処理が原因です` |
| S7 | 翻訳調の分析動詞を使わない | 「〜を示しています」「〜を示唆しています」「〜を物語っています」「〜が浮かび上がります」「〜に収斂します」がないか | `この結果は移行の難しさを物語っています` → 結果の数値そのものを書く。解釈が要るなら、E1 のとおり理由付きの別の文にする |
| S8 | 一般論で済ませない | 「多くの開発者は」「一般に」「現代のシステムでは」で始まる段落に、このリポジトリの具体 (人、コンポーネント、数値、パス) があるか | `多くのサービスでセッション管理は課題になっています` → 消す。書くなら `このリポジトリでは、直近 3 か月の修正 40 件のうち 11 件がセッション管理の修正です` のように書く |

### 3.3 構造

| 番号 | 検査 | 見る箇所 | 落ちる例 → 直し方 |
|---|---|---|---|
| S9 | 見出しは名詞句にする | 見出しが主張や問いかけになっていないか (「なぜ OIDC に統一すべきなのか」「セッション管理が教えてくれること」)。節の最初の文が見出しの言い換えになっていないか | 見出しを `認証方式` にし、主張は節の最初の文に書く (E2)。質問票の `title` は主張の言い切りにしますが、文書の見出しは読者が目次から節を探すために使うので名詞句にします |
| S10 | 定型の書き出し、締め、予告を書かない | 冒頭の「近年〜が注目されています」「ここでは〜について解説します」、末尾の「今後の展開が期待されます」「〜と言えるでしょう」、途中の「以下の 3 つの観点から説明します」「ここで重要なのは」がないか | 消す。冒頭は結論の一文 (E2) にし、末尾は決定事項か次の作業にする |
| S11 | 対比や否定で演出しない | 「単なる A ではなく B です」「A ではない。B でもない。C です」「シンプル。それだけ。」がないか | `単なる認証基盤の置き換えではなく、運用の見直しです` → `認証基盤を置き換え、あわせてセッションの監視を止めます` のように、する内容を直接書く。案を比べるなら違いを具体的に書く |
| S12 | 事実の後に意義を付け足さない | データの文の後に「これは〜を示しており」「〜が期待されます」が続いていないか | `試験環境での移行失敗は 0 件でした。これは新方式の信頼性の高さを示しています` → 前の文だけ残す |
| S13 | 並べる数は実際の数にする | 「3 つのポイント」「3 つの原則」のように、項目を 3 つに揃えていないか | 実際に 2 つなら 2 つ、4 つなら 4 つ書く。数を揃えるために足した項目は消す |
| S14 | 書式を増やしすぎない | 本文が 300 字に満たない節に小見出しを付けていないか。`- **ラベル:** 内容` の形の箇条書きが並んでいないか。✅ と ❌ で良し悪しを並べていないか | 短い節の小見出しは外す。ラベルと内容の組が並ぶなら、列名を定義した表にする (C4)。そうでなければ文で書く |

### 3.4 語彙

| 番号 | 検査 | 見る箇所 | 落ちる例 → 直し方 |
|---|---|---|---|
| S15 | 生成 AI が好む抽象語を撒かない | 「本質」「解像度」「腹落ち」「手触り」「熱量」「営み」「地に足のついた」がないか。体験や状況に「設計されている」と書いていないか (設計書の「設計」のような字義どおりの用法は対象外) | `要件の解像度を上げます` → `要件を画面ごとに書き出します` |
| S16 | 比喩の定型を使わない | 「羅針盤」「土台」「車の両輪」「DNA」「起爆剤」や、比喩としての「思考の OS」「ハックする」「インストールする」がないか | `この仕様書が開発の羅針盤になります` → 消す。役割を書くなら `実装で判断に迷ったら、この文書の決定事項に従います` と書く |
| S17 | カタカナ語とビジネス語を日本語に戻す | 普通の日本語で言える語をカタカナで書いていないか (「アライン」「レバレッジ」「プライオリティ」、約束の意味の「コミット」)。技術用語 (git の commit など) は B1 のとおりそのまま使う | `関係者とアラインします` → `関係者と方針を合わせます` |
| S18 | 冗長な文末と、言い切らない文末を使わない | 「〜することができます」「〜と言えるでしょう」「〜ではないでしょうか」がないか | `設定を変更することができます` → `設定を変更できます`。言い切れないなら F2 のとおり推測と書く |
| S19 | 強調の副詞を数値に置き換える | 「非常に」「とても」「かなり」「極めて」「大幅に」がないか | `応答が大幅に速くなります` → `応答時間の中央値が 420 ms から 180 ms になります (負荷試験、2026-09-22)` |
| S20 | 接続詞を重ねない | 「一方で」「しかしながら」「さらに」「加えて」「このように」が続く段落がないか | 半分を消し、文の順序で論理を示す |
| S21 | 論文調の自称を使わない | 「本稿」「本記事」「筆者」がないか | `本稿では` → `この文書では` |

### 3.5 記号

| 番号 | 検査 | 見る箇所 | 落ちる例 → 直し方 |
|---|---|---|---|
| S22 | ダッシュを使わない | 全角ダッシュ (―、──) と em ダッシュ (—、——) がないか | 補足は括弧、言い換えはコロンか改行、つなぎは読点にする。`Keycloak——認証サーバ製品——を使います` → `Keycloak (認証サーバ製品) を使います` |
| S23 | かぎ括弧は画面の文言と引用だけに使う | 形容詞や心情、普通の語を「」で囲んでいないか | `「軽い」処理` → `軽い処理`。画面の文言 (「ログイン」ボタン) と、人の発言の引用は囲む |
| S24 | 中黒で 3 つ以上を並べない。絵文字を使わない | 「認証・認可・監査」のような並列や、🚀 ✨ などの装飾がないか | `認証・認可・監査` → `認証、認可、監査`。絵文字は消す |

## 4. 採用しなかった規則

stop-ai-slop-jp と humanizer-ja は、主にブログやエッセイを人の声で書き直すためのスキルです。次の規則は、決定を記録する文書の読者の役に立たないか、ja-text-communication の規範とぶつかるので採用しません。

| 規則 | 元 | 採用しない理由 |
|---|---|---|

## 5. 通し方

1. 書く前に、1 章の 4 つを決めます。
2. 書いた後、3 章を 3.1 から順に見て直します。
3. 2 章を上から順に見て直します。
4. 機械で見つけられる癖を検索します。`Grep` ツールで、文書のファイルに次の正規表現を当てます。当たった行は 3 章の該当する番号で直します。字義どおりの用法 (git の「コミット」、設計書の「設計」など) と、コードブロックの中 (ディレクトリの木構造の罫線など) は残します。

   ```
   —|―|─|することができ|と言えるでしょう|ではないでしょうか|いかがでしたか|注目されています|期待されます|浮き彫り|物語って|示唆して|ケースバイケース|場合によります|一概には|本質|解像度|腹落ち|非常に|極めて|本稿|本記事|筆者|\*\*[^*]+([:：]\*\*|\*\*[:：])|\p{Extended_Pictographic}
   ```

5. 次の 5 つの問いに答えます。1 つでも不通過なら、対応する番号の検査に戻って直します。

   | 軸 | 問い | 対応する番号 |
   |---|---|---|
   | 決定 | 冒頭の一文と決定事項だけを読んで、読者が「いや、別の案にすべきだ」と反論できる具体的な決定があるか | E2、S1〜S5 |
   | 主体 | 各決定に、誰 (どの役割、どのコンポーネント) が何をするかが書いてあるか | C2、S6〜S8 |
   | 具体 | 数値に単位と範囲が、場所にパスが、名前に固有名があるか | D1、D3、D4、S19 |
   | 典拠 | 事実の文に典拠 (`file:line`、実行結果、回答) があり、推測は推測と書いてあるか | F1、F2 |
   | 削減 | 消しても意味が変わらない文 (前置き、見出しの言い換え、付け足した意義、保留の決まり文句) が残っていないか | S5、S9〜S12 |

6. 最後に、文書を頭から、声に出すつもりで通して読みます。息が続かない文、2 度読まないと意味が取れない文、同じ言い回しが続く箇所を直します。
