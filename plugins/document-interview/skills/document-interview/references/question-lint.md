# 質問文の自己検査表 — ja-text-communication の規範番号順

質問票 JSON を `open_form` に渡す前に、この表で自分の文を検査します。規範番号は `ja-text-communication` の SKILL.md (A〜H) のものです。対象の欄は `title`, `conclusion`, `glossary`, テーマの `name`, 問いの `title` と `cite`, 選択肢の `label`, `pros`, `cons`, 表の `title` と `columns`, `note.placeholder`, `globalNote.label` です。

Mod の検証 (`references/form-spec-v1.md`) は形しか見ません。文の意味はここで自分で検査します。この表で通っても、試問 (`references/preflight.md`) は省きません。書き手の自己判定は文脈を持っている分だけ甘いからです。

## 検査表

| 番号 | 規範 | 質問票での検査 | 落ちる例 → 直し方 |
|---|---|---|---|
| A1 | 専門用語・略語は初出で定義する | 問いや選択肢に出る略語 (OIDC, RBAC, SLA など) は `glossary` にあるか。1 行で定義しているか | `OIDC に統一します` だけ → `glossary` に `{ "term": "OIDC", "definition": "OpenID Connect。OAuth 2.0 の上で認証を行う標準です。" }` を足す |
| A2 | 固有名詞は初出で位置づけを添える | ツール名・ライブラリ名・他の文書名が出るとき、それが何で、なぜここに出るかが `cite` か `glossary` にあるか | `Keycloak を使う` → `Keycloak (認証サーバ製品) を使う`、または `glossary` に入れる |
| A3 | 自分が導入した内部要素は相手にとって未知 | Claude が付けた ID (`q1`, `tb1`, `t1`)、変数名、関数名、条件ラベルを問いの文や選択肢に出していないか。出すなら役割を説明しているか | `q1 で A を選ぶと sessionStore は不要です` → `初回ログイン時に自動移行する案 (A) を選ぶと、自前のセッション保存 (src/auth/session.ts の sessionStore) は不要になります` |
| A4 | 業界の常識を前提にしない | 「普通は」「一般に」で済ませている判断材料がないか。`pros` と `cons` は前提なしで読めるか | `pros: 標準的です` → `pros: 主要なクラウド 3 社 (AWS, GCP, Azure) の認証基盤がそのまま使えます` |
| A5 | 成果物ごとに用語を再導入する | 前のターンや前の質問票で定義した語でも、この質問票の `glossary` に入っているか | 2 枚目で `glossary` を空にした → 1 枚目の定義を再掲する |
| B1 | 英語術語は定訳 → 定着カタカナ → 英語のまま、の順 | 独自に訳した術語がないか | `前進認証` → `認証の事前検証 (pre-authentication)` のように定訳か英語のまま |
| B2 | 英単語に助詞・活用を直結しない。英複合語を展開する | `retrieve した`, `generic な`, `token-based で` のような書き方がないか | `session を migrate する` → `セッションを移行する`。`rate-limit 付き` → `回数制限 (rate limit) 付き` |
| B3 | 訳語だけで意味が通るか | 選択肢の `label` だけ読んで意味が取れるか | `label: "ハイブリッド"` → `label: "自動移行と再登録の併用"` |
| B4 | 造語・圧縮熟語・俗語・比喩を使わない | 「〜に落とす」「〜を流す」「〜を受ける」「認証寄せ」のような語がないか | `ログを流す先` → `ログの送信先`。`OIDC 寄せ` → `OIDC への統一` |
| B5 | 敬体で一貫させる | `conclusion`, `pros`, `cons`, `cite` の文末が「です・ます」で揃っているか。体言止めのメモ調が混ざっていないか | `cons: 離脱増` → `cons: 離脱が増えます` |
| C1 | 一文一義 | 問いの `title` は 1 文か。`conclusion` の各文は 1 つのことだけ言っているか。`pros` と `cons` はそれぞれ 1 行 1 事実か | `title: "移行をどうするか、またログの保持期間は"` → 2 問に分ける |
| C2 | 主語・目的語・授受関係を省かない。体言止めの圧縮句で判断を表さない | 「誰が」「何を」が抜けていないか。`label` が名詞の羅列になっていないか | `label: "自動移行"` → `label: "初回ログイン時に自動移行"` |
| C3 | 矢印連鎖の前提を先に説明する | `cite` や `cons` に `A → B → C` があれば、各矢印の前提が書かれているか | `cons: 失敗 → 切り分け困難` → `cons: 移行に失敗したとき、原因が認証側か移行側かの切り分けが難しくなります` |
| C4 | 表のセル・括弧・見出しに未説明の圧縮表現を置かない | 表の `columns` の意味を `title` で説明しているか。列名が 1 語で曖昧でないか (「状態」「値」など) | `columns: ["画面", "要否"]` → `title: "画面ごとの認証要否"`、`columns: ["画面", "認証 (必要 / 不要)", "備考"]` |
| D1 | 指示語より固有名 | 「これ」「その方式」「上記」が問いや選択肢にないか。各問は自己完結カードなので、他の問いを指さない | `cons: それに依存します` → `cons: 自動移行 (Q1 の A) に依存します` は不可。問いをまたぐ依存があるなら 1 問にまとめる |
| D2 | 重要な区別を助詞や含みで表さない | 「残す / 消す」「移動 / 複製」の違いが `label` に明示されているか | `label: "セッションも"` → `label: "自前セッションを残し、OIDC と併用する"` |
| D3 | パスは読み手の座標系で書く | `cite` のパスはリポジトリ直下からの相対パスか、絶対パスか。読み手が開ける形か | `cite: "session.ts:40"` → `cite: "src/auth/session.ts:40-88 に自前セッションの発行があります"` |
| D4 | 数値に単位・分母・範囲を添える | `cite`, `pros`, `cons` の数値に単位と何に対する値かが付いているか | `cons: 4 倍` → `cons: 保存費用が約 4 倍 (90 日保持に対して) になります` |
| D5 | 同一概念に同一の語 | 同じものを「利用者」「ユーザー」「会員」と呼び分けていないか。`title`, `conclusion`, 問い、選択肢で語を揃えているか | 揃える。用語表が要るなら `glossary` に置く |
| E1 | 主張には理由 | `conclusion` の各文に理由が (`cite` か本文で) 付いているか | `結論: OIDC に統一します` → `結論: 認証は OIDC に統一します。自前セッションの保守が月 2 件の障害の原因だからです (docs/ops/incidents.md:3-20)` |
| E2 | 要点先行 | `title` は主張の言い切りか (要約や疑問文ではないか)。`conclusion` は `結論:` で始まるか | `title: "認証方式について"` → `title: "認証方式は OIDC に統一する"` |
| E3 | 主張 → 根拠の順 | 問いカードは `title` (問い) → `cite` (根拠) → 選択肢の順になっているか。`cite` に主張を書いていないか | `cite: "OIDC が良いと思います"` → `cite` は事実だけ。判断は `pros` と `cons` に |
| E4 | 見出しと内容の一致 | テーマの `name` の下に、その名の問いだけがあるか。表の `title` と `columns` が一致しているか | テーマ「方式」の下にログ保持期間の問い → テーマ「運用」に移す |
| E5 | 質問には正面から答える形 | 問いの `title` に対して、各 `label` が答えの形になっているか | `title: "移行をどう扱いますか"` に `label: "検討する"` → 答えになっていない。落とす |
| E6 | 前言との矛盾を検査する | `conclusion` と選択肢の推奨が矛盾していないか。1 枚目の回答と 2 枚目の前提が矛盾していないか | `conclusion` で「移行期間は 2 週間」と言い切り、Q で「移行期間は?」と聞く → どちらかに |

| F1 | 事実的記述に典拠 | `cite` は `file:line` か実行結果か。「〜と言われている」がないか | `cite: "移行は難しいとされています"` → 落とす。調べて事実で決まるなら問いごと消す |

| F3 | 一次情報を優先 | `cite` は原典 (コード、設定、実測) か。記憶や二次資料から引いていないか | README の記述より、実際の設定ファイルの行を引く |
| F4 | ソース由来と自作の例を区別 | 選択肢の `label` や `cons` の例が自作なら、自作と分かる書き方か | `cons: 例えば A 社ではこうなった` → 出典があるなら `cite` に、無いなら消す |
| F5 | 日付・バージョンは現時点で確認 | `cite` の実測値に取得日を添えているか。バージョン依存の話に対象バージョンがあるか | `cite: "Claude Code 2.1.278 で確認 (2026-09-22)"` |

## 通し方

1. 上から順に、質問票の全欄を対象に見ます。落ちた箇所は直します。
2. 続けて、`references/document-lint.md` の AI 臭の検査のうち S3 (曖昧な断言)、S6 と S7 (モノを主語にした書き方と翻訳調の動詞)、S15〜S24 (語彙と記号) を、同じ欄に当てます。
3. 直した後に、問いの数がまだ 2〜5 問か、`cite` が全問にあるか、`recommended` が各問 1 つ以下かを見ます (Mod の検証で落ちる項目)。
4. 次に `references/preflight.md` の試問へ進みます。
